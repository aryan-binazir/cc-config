PR #412 — one shared rate limit per tenantGeneric PR Explainer · html companion

System
The billing API server. Requests arrive over HTTP, gRPC, or the batch CLI, go through the Orchestrator, pass policy checks, and reach Storage.
Problem
Rate limits were enforced separately in each of the three entry points. A tenant that mixed HTTP and gRPC calls got three budgets instead of one.
Fix
One Limiter in Policy, keyed on the tenant, called once by the Orchestrator. The three local checks are deleted.

Read left to right: a request enters through api.HTTPHandler, api.GRPCServer, or cli.RunBatch; each calls orchestrator.Run, which asks policy.Limiter.Allow whether this tenant is over budget; only then does storage.Store write it.

orchestrator.Run takes over the rate-limit check removed from api/http.go, api/grpc.go, cli/batch.go · added to orchestrator/run.go

Each entry point kept its own counter, keyed on the connection, and returned 429 itself. Three copies, three budgets.

// api/http.go (same in grpc, cli)
if !limits[conn.Key()].take() {
  return http.Error(429)      
}                             
orchestrator.Run(req)

Run asks Limiter once, before any other policy. Limiter counts per tenant, so all entry points share one budget. Entry points just call Run.

// orchestrator/run.go
if !limiter.Allow(req) {      
  return ErrRateLimited // 429
}                             
applyPolicies(req)
store.Write(req)

types.Request gains a Tenant field types/request.go

The request didn't know which tenant sent it; only the connection did.

type Request struct {
  ID      string
  Payload []byte
}

Each entry point fills Tenant from its own auth (token, connection metadata, --tenant flag). Limiter keys on it.

type Request struct {
  ID      string
  Tenant  string
  Payload []byte
}
